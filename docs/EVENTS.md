# DevPilot event and API contract

Each WebSocket message is a JSON object:

```json
{
  "id": 42,
  "ts": 1790000000000,
  "mission_id": "m_example",
  "type": "test_result",
  "agent": "sentinel",
  "task_id": null,
  "code_rev": "r1:sha256:<tree-hash>",
  "verified": true,
  "payload": {
    "check_id": "unit",
    "outcome": "passed",
    "exit_code": 0,
    "duration": 50,
    "isolation": "isolated"
  }
}
```

`id` is a globally increasing SQLite event ID, not a per-mission sequence. `ts` is Unix milliseconds. `task_id` and `code_rev` can be null. `verified` means the service observed the stated fact; it does not mean a test passed or a model conclusion is true. Plans, model messages, and model review conclusions are claims. Staleness is conveyed by separate events, without modifying the original event. The payload of each `test_result` includes `isolation`, either `isolated` or `unisolated`, identifying the configured runner. The frontend must block approval when a relevant test result is `unisolated`. `isolation` is not stamped on other event types. Unisolated missions do not emit `approval_needed`: they escalate with `ISOLATION_UNAVAILABLE`.

Connect to `/ws?mission=<id>` for replay followed by live events. `after=<event-id>` resumes strictly after that global ID; clients should deduplicate by `id`. `GET /missions/:id` returns the mission projection and its `watermark`.

## Payloads by type

The following describes fields the service emits. Fields identified as optional occur only for the stated variant. Consumers should tolerate additional fields as the contract grows.

| `type`            | Payload fields                                                                                                                                                                                                                                                                                                  |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mission_started` | `repo`, `request`, `base_hash`, `deadline` and `deadline_max` (initial Unix-millisecond deadline and maximum before any approval pause), `fix_extension_ms`, `mission_cap` (initial turn cap), `mission_cap_max`, `turn_extension_per_fix`, `samurai_turn_extension_per_fix`, `samurai_turn_max`, `suite_id` (string or null), `mode` (`multi` or `baseline`), `baseline_of` (mission ID or null), `paired_mission_id` (mission ID or null).                                                                                                      |
| `plan`            | `version`, `criteria`, `tasks`, `reason_event_ids`. Criteria and tasks are model claims; each task includes `id`, `title`, `role`, and `status`. The baseline `test_result` precedes the plan and is cited in `reason_event_ids`.                                                                               |
| `task_update`     | `task_id`, `previous_status`, `status`, `reason_event_ids`; a send-back with `status: "blocked"` includes the updated `deadline` (Unix milliseconds).                                                                                                                                                                                                                                                     |
| `agent_msg`       | Usually `to`, `message`, and optionally `evidence_event_ids`. Review completion also includes `findings`; security completion may include `scanner_findings` and `scanner_event_id`. A pairing announcement includes `baseline_of` and `paired_mission_id`.                                                     |
| `tool_call`       | `call_id`, `tool`, sanitized `arguments`, `job_id`. Edit content is not included in arguments (`edit_file` records only `path`). Arguments of every other tool, including `submit_plan`, are included after credential and secret redaction; strings are capped at 2,000 characters. Usage counter keys such as `input_tokens` are not redacted.                                                                                                                                      |
| `tool_result`     | `call_id`, `ok`, and either `data` or `error: {code, message?}`. `COMMAND_NOT_ALLOWED` also supplies `allowed_check_ids`; `PROTECTED_FILE` rejects edits to test and test-configuration files. `REVIEW_SUBMIT_REQUIRED` closes reviewer inspection for this revision. A nonzero test exit is an observed test failure, not a tool-execution error.                                     |
| `test_result`     | Project check: `check_id`, `outcome` (`passed` or `failed`), `exit_code`, `duration` in milliseconds, and optionally `phase: "baseline"`. Acceptance: `suite_id`, `outcome`, `criteria: [{id, passed}]`. `isolation` identifies the runner. Private suite source and raw private test output are not published. |
| `finding`         | `finding_id`, `severity`, `blocking` (boolean), `action` (`open`, `resolve`, or `sent_back`), `title`, `detail`, and `evidence_event_ids`; reviewer findings may include `in_scope`, `evidence` (`path` and `line`, or `failing_case`), `advisory_reason`, `resolution_evidence` (`path` and `line`; present when a reviewer's addressed claim on its own critical finding was accepted), `unaccepted_resolution` (why an addressed claim on a critical was rejected; the finding stays blocking), and `carried_forward: true` (a blocking critical the reviewer omitted, kept open). `finding_id` is stable per reviewer and normalized title across passes; different reviewers reporting the same title get different IDs. `sent_back` records that a blocking finding was returned to the editor for a repair cycle. A refused `PROTECTED_FILE` or `INVALID_PATH` file-tool call also emits a non-blocking `info` finding from `orchestrator` (title `Protected file edit blocked` or `Path escape blocked`) with `tamper: {tool, path, code}` and the refused `tool_result` in `evidence_event_ids`.                                                                           |
| `diff`            | `text` is the cumulative textual diff from the mission's original base to this revision; `artifact_id` identifies the same text, `base_hash` is the original tree hash, `revision` is the candidate revision, and `changed_paths` lists paths changed in this edit. Binary changes are summarized in text.      |
| `approval_needed` | `approval_id`, `evidence_ids`, `tree_hash`, `decision: null`, `active_elapsed_ms`, `wall_elapsed_ms`, `deadline_paused: true`, and `deadline_remaining_ms`. The envelope's `code_rev` identifies the revision.                                                                                                                                                                                            |
| `approval_result` | The same `approval_id`, `evidence_ids`, and `tree_hash`, with `decision` set to `true` or `false`.                                                                                                                                                                                                              |
| `escalation`      | `reason`, `question`, `relevant_event_ids`, `evidence_ids`, `active_elapsed_ms`, and `wall_elapsed_ms`. For `TURN_LIMIT` and `DEADLINE`, `artifact_id` identifies a redacted debug artifact containing the last available model reply per role.                                                                                                                                  |
| `stale`           | `old_revision`, `new_revision`, `affected_evidence_ids`, `reason`.                                                                                                                                                                                                                                              |
| `usage`           | `{"per_agent": {"<agent>": {"turns": 0, "input_tokens": 0, "output_tokens": 0}}, "total": {"turns": 0, "input_tokens": 0, "output_tokens": 0}, "budget": {"<role>": 0}, "mission_cap": 44, "pass_turns": {"<role>": 0}, "review_pass": {"code_rev": "r1:sha256:...", "turns": {"shadow_review": 0, "shadow_security": 0, "verifier": 0}}}`. `per_agent` and `total` are cumulative for the mission. `budget` holds effective role caps, including the current Samurai cap, and `mission_cap` is the current effective mission-wide cap. `pass_turns` counts all model roles at the current revision; `review_pass` identifies that revision and repeats the reviewer counts, including zeroes. A reservation, turn-cap increase, and later provider token report can each emit a snapshot. |
| `mission_done`    | `status` (`COMPLETED`, `REJECTED`, or `ESCALATED`), `active_elapsed_ms`, `wall_elapsed_ms`; cumulative `per_agent` and `total` in the same shape as `usage`; `baseline_of`, `paired_mission_id`, `evidence_ids`, and `unresolved_findings`. `applied_revision` or `recovered` may be present.                                                           |

When isolated verification passes and the mission reaches the approval gate, every planned task that is not already complete receives a `task_update` with `status: "completed"` before `approval_needed`. Its `reason_event_ids` are the gate's `evidence_ids`, and `previous_status` reflects the latest recorded task status. Escalations preserve the latest task statuses rather than marking unfinished work complete.

`shadow_review`, `shadow_security`, and any verifier model calls each receive the corresponding `budget` number of turns per candidate revision. Multiple sessions on the same revision share that allowance; a new revision gets a fresh one. Other roles, including the single-agent baseline, use their role allowance across the whole mission. The mission cap and cumulative totals span all revisions. The verifier currently uses a test harness rather than model calls, so its review-pass count is normally zero. `TURN_LIMIT` and `DEADLINE` escalations cite recent relevant event IDs and describe the exhausted role/revision/mission budget or deadline. Each deadline or turn-limit artifact is limited to approximately 4 KB and redacted; raw model replies are not included in events. Earlier recorded usage snapshots may lack the newer `budget`, `mission_cap`, `review_pass`, and `pass_turns` fields. A README or documentation edit emits a non-blocking informational `finding`; protected test/configuration edits return `PROTECTED_FILE`.

The initial wall-clock deadline is `DEVPILOT_BASE_MISSION_SECONDS` (default 240 seconds). Each of up to three send-backs extends it by `DEVPILOT_FIX_EXTENSION_SECONDS` (default 60 seconds, 0 disables extensions), capped at `DEVPILOT_MAX_MISSION_SECONDS` of elapsed mission time excluding approval wait (default 420 seconds, at least the base). Settings use integer seconds. The deadline pauses in `AWAITING_APPROVAL` and resumes with the saved remaining time for an approved apply. There is no separate approval timeout. `GET /missions/:id` includes `deadline_paused` and `deadline_remaining_ms` (null outside the approval gate); its `deadline` during the pause is the prior timestamp, and is updated when the timer resumes. There is no global model/tool queue: concurrent missions each have an independent wall-clock deadline that includes provider and container waits. `active_elapsed_ms` is monotonic elapsed orchestration time up to approval or termination, counting concurrent jobs once and excluding the subsequent human approval wait; `wall_elapsed_ms` is elapsed wall time from mission creation to the event. These are not CPU-time or queue-excluded measurements. The current deadline is updated in the blocked task event and send-back agent message. Reviewer findings require `in_scope: true` and evidence to block; the service checks that a cited file/line exists or that a failing case is supplied, but does not independently establish its truth or relevance. Findings are keyed by reviewer and normalized title, so one reviewer cannot repeat, address, or resolve another reviewer's finding. Previously sent-back non-critical findings do not block again; a repeated critical stays blocking. A reviewer marks its own critical finding addressed only with `addressed: true` plus `resolution_evidence` naming an existing file and line in the candidate, and, if the critical blocked an earlier candidate, only after the tree changed; omitting a blocking critical from a later report does not resolve it. Generic scanner patterns and unsupported or out-of-scope findings are advisory.

The mission turn cap starts at 44 (52 for feature requests) and increases by 16 after each reserved fix cycle, to a maximum of 100. Set `DEVPILOT_MISSION_TURN_LIMIT` for the initial cap, `DEVPILOT_TURN_EXTENSION_PER_FIX` for the increment (0 disables it), and `DEVPILOT_MAX_MISSION_TURNS` for the maximum. The default maximum rises with an initial cap above 100; explicitly configured values must be integers with `1 <= initial <= maximum <= 200` and `0 <= increment <= 200`. Usage emits the new effective cap as soon as a fix is reserved; cumulative usage is never reset.

Samurai starts with 16 turns (22 for feature requests) and gains 8 per reserved fix cycle, subject to the effective mission cap and a separate maximum of 48. Configure the increment with `DEVPILOT_SAMURAI_TURN_EXTENSION_PER_FIX` and the maximum with `DEVPILOT_MAX_SAMURAI_TURNS`; the increment must be 0–200 and the maximum must be at least Samurai's initial budget and at most 200. `budget.samurai` reports the current effective cap; cumulative Samurai usage does not reset.

Previously recorded delta-form usage events are converted to cumulative snapshots when replayed, including on resumed connections. Acceptance `test_result` events publish only collected test IDs and boolean outcomes. The trusted suite is collected before candidate execution and run in a fresh pytest process that uses an RPC proxy to a separate candidate worker. Missing or malformed JUnit, a changed collection, unexpected IDs or exit status, and timeouts do not satisfy the acceptance gate. Infrastructure failures can instead produce an `escalation` and `mission_done` without a `test_result`. In unisolated mode the shared host account and filesystem are not a tamper-proof boundary.

Tokens come from the provider's reported `prompt_tokens` and `completion_tokens`, not an estimate of text length. Totals contain only counts actually reported before the mission ended. An absent provider usage report contributes zero to the reported total and is **not** evidence that no tokens were used. Mock responses may include scripted usage; otherwise they report no token counts. Every attempted model call consumes a turn even when the call fails or times out.

## Missions, pairing, and artifacts

`POST /missions` accepts `{"repo":"stock","request":"<registered request>"}` and returns `202 {"mission_id":"m_...","id":"m_..."}`, with identical IDs. `mode` can be `multi` or `baseline`. Unknown request text returns `400 {"error":"UNKNOWN_REQUEST","message":"...","repo":"stock","valid_requests":["<exact text>", ...]}`. `GET /requests` returns `{"requests":[{"repo","request","label","has_acceptance"}]}` for UI dropdowns (no suite paths or digests).

To link a baseline, post `{"repo":"stock","request":"<same request>","mode":"baseline","paired_mission_id":"<multi-mission-id>"}`. The referenced mission must be a multi-agent run for the same repo and request, with no existing pair. The baseline starts from an independent copy of that run's original base and uses the same suite; a changed or unavailable base or suite rejects pairing. A baseline's `baseline_of` and `paired_mission_id` both point to the multi-agent run; the multi-agent projection's `paired_mission_id` points to the baseline. A pairing announcement is also appended to the multi-agent event stream. The multi-agent run's already-emitted `mission_started` event is not rewritten.

When a structured model reply is rejected, an `agent_msg` contains a schema-specific reason and an `artifact_id` for a redacted, truncated debug file at `runtime/artifacts/<mission-id>/<artifact-id>.txt`. Raw reply text and model reasoning are not put into the event stream; the mission-scoped artifact API serves these redacted debug files as plain text. A second invalid reply escalates with `MODEL_RESPONSE_INVALID` and cites the rejection messages and associated tool events.

`GET /missions/:id/artifacts/:artifactId` returns a mission-scoped diff or redacted debug artifact's UTF-8 text with `Content-Type: text/plain` and `X-Content-Type-Options: nosniff`. Artifact IDs are scoped to the mission: an unknown or mismatched ID returns `404`. Diff artifacts contain exactly the `text` from their `diff` event. Private acceptance artifacts are not exposed.

`POST /missions/:id/approve` accepts `{"approved":true}` or `{"approved":false}` only for the outstanding approval. After a decision, any further approval or rejection returns `409`. Approval is for the exact revision and tree hash in `approval_needed`.

Each mission starts with an independent seed copy and applies only to `runtime/missions/<mission-id>/target/current`. An unchanged or reverted candidate escalates with `NO_CHANGES` and never requests approval. In unisolated mode, even a passing candidate escalates with `ISOLATION_UNAVAILABLE` rather than requesting approval. For the ambiguous titles scenario, `relevant_event_ids` and `evidence_ids` include the `TOOL_DISABLED` result event ID.

Cross-origin requests require an exact origin in `DEVPILOT_ALLOWED_ORIGINS`, a comma-separated list; its default is `http://localhost:5173,http://127.0.0.1:5173`. Same-origin requests are also accepted. Allowed browser preflights and responses include CORS headers; other origins are rejected.
